PROJECT 01 / 04

AI Research Agent

From a question to a cited research report — automatically.

A full-stack research workspace that turns a natural-language topic into a structured, source-backed report. Runs a multi-step agentic workflow instead of stopping at a list of search results: an agentic research workflow, not a chatbot with a search box.

View Live → View Source
Next.jsReactTailwind CSS FastAPIPythonGoogle Gemini TavilyDocker ComposeVercelRender
Engineering decisions & why this matters

Why an agentic workflow, not a single prompt? Splitting the job into plan → search → collect → synthesize → cite → export keeps each stage grounded in evidence, instead of asking one model call to both know facts and write well.

Why Gemini + Tavily? Gemini handles query planning and cited synthesis; Tavily supplies real web and image retrieval so the report is source-backed rather than hallucinated.

Why Docker Compose + split hosting? The Next.js frontend deploys to Vercel and the FastAPI backend to Render independently, containerized with Docker for local parity with production.

What it demonstrates: agentic workflow design, LLM planning and synthesis, citation-aware generation, PDF export, and a fully deployed two-service architecture.

Product flow
01Question — user asks a research topic in plain language
02Planning — Gemini turns it into focused search queries
03Discovery — Tavily retrieves web + image sources
04Synthesis — Gemini writes a structured, cited report
05Export — report renders with citations, visuals & PDF export
2 deployed services 1 ★ on GitHub Live in production
PROJECT 02 / 04

Real-Time AI Voice Chat

A voice assistant you can interrupt mid-sentence.

A real-time voice conversation system running entirely on local AI models — speech recognition, a local LLM, and text-to-speech, connected with true barge-in handling: the assistant stops speaking the moment a new request starts, instead of finishing its sentence first.

View Source
PythonFastAPIWhisper OllamaLlama 3.2Glow-TTS DockerDocker Compose
Engineering decisions & why this matters

Why local models over a cloud AI API? The full pipeline — Whisper for speech-to-text, Ollama running Llama 3.2 for reasoning, Glow-TTS for speech output — runs on the user's own machine, with no cloud AI dependency for the conversation itself.

Why build barge-in at all? Most voice assistants follow a strict speak → wait → respond cycle. Interrupting an in-progress response and starting a new turn is a genuinely harder real-time systems problem than typical request/response chat.

What it demonstrates: real-time audio pipelines, local LLM integration, interruption handling, and latency-aware system design — fully Dockerized.

Interruption flow
01Assistant speaking — TTS is mid-response
02User starts speaking — new speech detected
03Response interrupted — current turn is dropped
04New request processed — Whisper → Ollama → TTS
05New response starts — conversation continues
Fully local inference Dockerized backend
PROJECT 03 / 04

AI-Powered PDF Q&A Tool

Upload a PDF. Ask it questions. Get grounded answers.

A retrieval-augmented generation (RAG) application: upload a PDF, and ask questions about its content in natural language. Answers are retrieved from the document itself rather than generated from the model's general knowledge.

View Source
PythonStreamlitPyPDF2 Sentence TransformersFAISSGroqLlama 3.1 8B
Engineering decisions & why this matters

Why RAG over just prompting the model? Chunking the PDF (800 characters with overlap) and retrieving only the relevant chunks via FAISS similarity search keeps answers grounded in the actual document instead of the model's memory.

Why local embeddings (all-MiniLM-L6-v2)? Generating embeddings locally with Sentence Transformers keeps the retrieval step fast and free, reserving the API call for the final answer generation via Groq's Llama 3.1 8B Instant.

What it demonstrates: a working RAG pipeline end to end — extraction, chunking, embedding, vector search, and grounded generation — with retrieved context surfaced to the user for transparency.

RAG architecture
01PDF upload → text extraction (PyPDF2)
02Chunking — 800 chars with overlap
03Embedding — Sentence Transformers → FAISS index
04Retrieval — similarity search on the question
05Answer — Groq Llama 3.1 8B, grounded in retrieved chunks
RAG pipeline Local embeddings
PROJECT 04 / 04

YouTube AI Summarizer

Watch less. Learn faster.

Paste a YouTube link, pick a summary style, and get a transcript-grounded summary in seconds — no download, no manual note-taking. Intentionally small in scope, but a complete end-to-end AI workflow: retrieval, prompt control, and generation.

View Source
PythonStreamlityoutube-transcript-api GroqLlama 3.1 8B
Engineering decisions & why this matters

Why transcript-grounded, not video-download? Pulling captions via youtube-transcript-api avoids downloading video, keeping the app lightweight and fast.

Why multiple summary styles? Concise, bullet-point, or detailed output lets the same pipeline serve lecture revision, interview scanning, and tutorial pre-reading differently.

What it demonstrates: external data retrieval, prompt-controlled generation, and a small but genuinely usable AI tool — not every project needs to be maximal to be worth shipping.

Product flow
01URL — paste a YouTube link
02Transcript extraction — captions pulled automatically
03Style selection — concise / bullets / detailed
04Generation — Groq + Llama 3.1, grounded in transcript
05Output — summary + raw transcript view
